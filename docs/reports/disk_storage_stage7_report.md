# Отчёт этапа 7: границы transaction-private spill

Дата: 2026-08-28.

## Решение

Production spill пока **не добавлен**. Benchmark-first проверка показала, что он не устраняет
текущую причину роста памяти: каждый следующий local commit заново материализовал весь граф, а
публичный корень продолжал удерживать эту копию после записи на диск. Кроме того, массовое
создание атомов упиралось в квадратичную проверку уникальности `RecordId`, а лимит write-set не
учитывал payload крупных свойств.

Исправлены три предшествующих дефекта:

1. оценка write-set обходит вложенные `PropertyMap`/`Value` и отклоняет крупную транзакцию с
   `FG-54F07` до WAL и публикации;
2. уникальность `RecordId` поддерживается существующим `RapidHashSet`, поэтому вставка больше не
   сканирует все nodes и edges;
3. после local commit Datastore публикует disk-backed `LocalGraph`, а не долгоживущий полный
   `MaterializedGraph`; старые snapshot по-прежнему удерживают собственный WAL/home snapshot.

Оценка write-set учитывает payload, но пока не является точным счётчиком всех heap allocation.
В ней уже учитывается основной опасный случай — property payload, включая вложенные
значения. Перед production spill отдельно нужны оценки крупной adjacency, составных
идентификаторов и вложенных графов.

## Что означает spill

Transaction-private spill переносит часть **незакоммиченных** изменений одной транзакции из RAM
во временный файл. Он нужен только для одного неделимого атомарного commit, который обоснованно
превышает лимит 256 МиБ. Корректный путь должен:

1. хранить в RAM ограниченный набор atom-level delta;
2. не публиковать временные данные в WAL, checkpoint или другим readers;
3. на commit повторно проверить FCW/SSI и применить delta к актуальному snapshot;
4. опубликовать транзакцию одной границей видимости либо удалить spill при abort/crash.

Spill не исправляет полную материализацию и не ускоряет обычный запрос. Для разбиваемого bulk
import несколько ограниченных commit уже дают bounded RAM без нового recovery-протокола.

## Диагностический benchmark

В `src/storage/benchmarks.rs` сохранён ignored release-тест
`disk_storage_stage7_spill_probe`. Он поддерживает:

- `FG_STAGE7_WORKLOAD=properties|atoms`;
- `FG_STAGE7_MODE=atomic|segmented`;
- `FG_STAGE7_PAYLOAD_MIB`, default 320;
- `FG_STAGE7_BATCH_MIB`, default 64;
- `FG_STAGE7_ATOMS` для точного atom-heavy прогона.

Byte-heavy workload создаёт детерминированные несжимаемые свойства по 1 МиБ. Atom-heavy workload
создаёт узлы без свойств. Benchmark раздельно печатает attempted/committed объём, staging,
commit, общее время, видимый результат и RSS. Каждый приведённый batch-result получен отдельным
процессом в bench-профиле на Windows 10.0.22631, Rust 1.97.1 и KIOXIA BG5.

## Исправление лимита write-set

До исправления atomic-транзакция с 320 МиБ свойств проходила лимит 256 МиБ: 320 значений по
1 МиБ оценивались примерно как 80 КиБ, потому что учитывалось только число `DirtyTarget`.

| Atomic 320 МиБ properties | Staging | Commit | Всего | RSS после | Результат |
|---|---:|---:|---:|---:|---|
| до исправления | 177,5 мс | 785,4 мс | 977,7 мс | +390,9 МиБ | committed |
| после исправления | 189,9 мс | 0,2 мс | 203,4 мс | +320,0 МиБ | `FG-54F07`, committed 0 |

Проверка выполняется до commit lock, WAL и публикации. Отдельный regression-тест подтверждает,
что после отказа граф остаётся пустым.

Atom-heavy транзакция из 1 048 577 узлов также превышает консервативный лимит и завершается
`FG-54F07`: staging 0,80 с, проверка/commit 0,09 с, published nodes 0.

## Устранение O(n²) проверки `RecordId`

До исправления `ensure_unique_record` для каждой вставки линейно обходил все живые nodes и
edges. Удвоение числа узлов увеличивало staging примерно в четыре раза:

| Узлы | Staging до исправления |
|---:|---:|
| 32 768 | 5 072,9 мс |
| 65 536 | 20 963,0 мс |
| 131 072 | 91 011,2 мс |

После добавления COW-индекса `RapidHashSet<RecordId>` 131 072 узла создаются за 80,0 мс —
ускорение staging примерно в 1 137 раз. Индекс общий для всех путей `Graph`, а не специальный
benchmark fast path. Тест проверяет межтиповые коллизии node/edge и повторное использование id
после удаления.

## `mimalloc`: retention и живая материализация

Retention не создаёт Rust-объекты повторно. После `free` mimalloc может оставить освобождённые
pages/segments в своих аренах для следующей allocation вместо немедленного возврата Windows.
Поэтому RSS включает логически свободную, но удерживаемую allocator память.

Пять segmented commit по 64 МиБ после исправлений дали следующие медианы трёх процессов:

| Настройка | Staging | Commit | Всего | Max staged RSS | RSS после commit |
|---|---:|---:|---:|---:|---:|
| default mimalloc | 2 292,5 мс | 3 426,2 мс | 5 725,7 мс | +976,6 МиБ | +1 946,0 МиБ |
| `MIMALLOC_PURGE_DELAY=0` | 3 208,3 мс | 5 355,3 мс | 8 568,4 мс | +450,5 МиБ | +2,4 МиБ |

Немедленный purge доказывает, что почти весь остаточный RSS default-запуска — retention, а не
живой граф или утечка. Одновременно он увеличивает общее время примерно на 50%, поэтому
глобально включать его нельзя.

Падение RSS после purge с прежних +321,9 МиБ до +2,4 МиБ подтверждает второе исправление:
Datastore больше не удерживает materialized local root после commit. Оставшийся пик около
450 МиБ возникает **до** публикации, пока mutable transaction действительно содержит полный
граф. Его нельзя убрать настройкой аллокатора.

## Оставшаяся причина роста

Текущий `edit_graph` материализует полный disk-backed граф при каждой новой транзакции. Поэтому
segmented workload снова читает и копирует уже записанный префикс, а пик растёт с размером
графа. Правильная следующая граница — delta-oriented mutation/import, где транзакция хранит
только изменённые атомы и страницы. Лишь после этого spill сможет вытеснять именно delta, а не
очередную полную копию.

## Gate перед возвратом к production spill

- пройти оставшийся Windows sync gate этапа 5; Linux/NVMe остаётся отложенным release-gate;
- добавить delta-oriented local mutation/import без полной материализации;
- покрыть лимитом крупную adjacency, составные идентификаторы и nested graph payload;
- повторить atomic/segmented benchmark больше 256 МиБ на реальном неделимом workload;
- только затем проектировать private spill format, crash cleanup и atom-level rebase.

До этого действует простой контракт: крупная property-транзакция отклоняется `FG-54F07` до
публикации, а разбиваемый import выполняется ограниченными commit.
